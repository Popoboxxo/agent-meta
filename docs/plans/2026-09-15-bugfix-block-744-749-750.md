## Global Constraints

1. **The approved spec is the single source of truth.** Contracts bind on file + symbol + exact string; the line numbers in this plan are hints and may drift after the first edit.
2. **No hand-editing of generated artifacts.** `.claude/`, `.agents/`, `.gemini/`, `.opencode/` are sync outputs. Changes there may only be produced by `python scripts/sync.py` in Task 4.
3. **TDD per task.** Every task observes a red test before its implementation step and a green run after it; a task is done only when the green run was actually executed.
4. **Verification commands are unfiltered.** No `rtk` prefix on any command in this plan. Every command redirects stdout+stderr into `.tmp/verify/<name>.log` and prints the exit code separately (issue #753); `.tmp/` is the sanctioned sandbox and the only place Task 5 writes to.
5. **No provider-name literal, no `if provider ==`.** Provider differences stay config-key/capability driven (AC-X2).
6. **Commit/push are withheld.** The spec's approval covers implementation only. Every commit step below is release-gated: it runs only after the user lifts the hold, and only via the `git` role.
7. **Ownership is single-writer.** Each hand-authored file appears in exactly one task's `Files:` block. Generated outputs are not write ownership and are never listed as `Modify:`/`Create:`.
8. **The Bug-C guard is not a Task-3 done criterion.** Its scan roots include the 12 managed provider artifacts, which only Task 4 rewrites; Task 3 proves the hand-authored roots are clean and records the expected 12-artifact offender list, Task 4 turns the guard green.
9. **No worktree isolation.** All tasks work directly in the project directory.
10. **No scope beyond the spec.** Non-goals of the spec apply verbatim: no `cwd` in the stdio builder, no new probe mechanism, no JSON schema for the catalog, no label changes, no severity change of the gate.

## Ownership decision — `docs/CODEBASE_OVERVIEW.md`

**Decision: `docs/CODEBASE_OVERVIEW.md` belongs wholly to Task 3.** Task 1 does not touch it; Task 1's `Files:` block therefore excludes it.

**Justification.** The file requires three edits for this block: `:1071` and `:1661` (Bug C, Task 3) and `:1166` (Bug A path, which the task decomposition listed under Task 1). Splitting one file across two tasks is the exact anti-pattern `check_plan_file_overlap` rejects, so one task must own it. Task 3 is the correct owner because it holds the majority of the lines (two of three) and it also owns the other two doc files of the same bug block (`docs/guides/context-block-inventory.md`, `ARCHITECTURE.full.md`), so the Bug-C doc consistency is produced by one writer. Task 3 therefore also performs the `:1166` Bug-A path edit — a single-writer transfer of that one line, not a second ownership claim. Task 1 keeps `docs/RELEASE_GATES.md`, and the complete AC-A3 grep runs in Task 5 across all three paths.

**Consequences to know before dispatch (static-analysis caveats, no write conflict).** The hand-authored files are disjoint: no path is written twice. The static affinity check (`scripts/lib/file_affinity.py`) additionally derives *couplings* from markdown references and Python import edges, and two of those are expected here. Both are read/mention relations, not writes, and neither requires sequentialization — all three tasks stay in parallel group A and all finish before the Task 4 barrier:

1. **Doc reference T3 → T1:** `docs/CODEBASE_OVERVIEW.md:1136` and `:1329` name `docs/RELEASE_GATES.md`. The checker compares a doc's references against the other task's write set, so it can report a coupling between Task 3 (`docs/CODEBASE_OVERVIEW.md`) and Task 1 (`docs/RELEASE_GATES.md`). Task 1 writes that file; Task 3 only mentions the path. The spec-mandated lines that name `config/plugin-catalog.yaml` produce the same mention-vs-write relation with Task 2 after the doc sweep.
2. **Import edge T2 → T3:** `tests/test_plugin_catalog_migration_invariant.py` imports `from lib.mcp import _generate_rule_content`, which resolves to `scripts/lib/mcp.py` (Task 3's file). Reading a module under test is not a write to it; Task 3 edits the module's strings, Task 2 edits its own test's assertions, and neither edits the other's file.

If the harness refuses to dispatch on either finding, treat it as this documented false positive. The alternative for (1) — moving `docs/RELEASE_GATES.md` into Task 3 — is available but was rejected because the task decomposition binds that file to Task 1.
