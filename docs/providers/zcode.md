## What is ZCode?

The official Z.ai harness for **GLM-5.3** — an ADE (Agentic Development Environment),
available as Desktop app and CLI. NOT the community clones (`simonyos/Z-CODE`,
`zmccyy/ZCode--CLI--tool`, `kodyberry23/zcode`).

Registry key: **`ZCode`**. Context file: **`AGENTS.md`** (shared cross-tool standard).

---

## Directory and file structure

```
AGENTS.md                  ← Project context + managed block + session-start bootstrap block
.zcode/
  agents/                  ← Agent definition store (generated by agent-meta)
    developer.md
    orchestrator.md
    ...
  config.json              ← Workspace settings (canonical, schema-documented; MCP: mcp.servers)
  skills/                  ← Skills (verified, workspace scope)
  snippets/                ← Snippets (generated)
  pending-tasks.md         ← Lifecycle tasks (gitignored)
  3-project/               ← Extensions read by agents at runtime

~/.zcode/
  agents/                  ← User-level subagents (auto-loaded by the harness)
  v2/config.json           ← Model configuration (UI-managed — NOT written by agent-meta)
  cli/config.json          ← User CLI config (MCP, permissions, plugins, hooks)
  skills/                  ← User-level skills
  commands/                ← User-level commands
```

## Agents as definition store + bootstrap

ZCode supports native subagent dispatch, but **workspace-level `.zcode/agents/` is
not (yet) verified to auto-load** — only user-level `~/.zcode/agents/*.md` auto-loads
(V18). agent-meta therefore generates the files anyway (single source of truth for
the roster, versioned in git) and consumes them via a **session-start bootstrap
block** in the managed `AGENTS.md` — ZCode is the **only provider besides Gemini
with a bootstrap block**.

`config/provider-bootstrap.yaml` → `ZCode`: `mechanism: api-based` (legacy
BootstrapEngine name for "inject bootstrap instructions into the context file" —
same handler as Gemini), `action: inject-bootstrap-instructions`,
`instructions_mode: static` (static instruction text instead of Gemini's generated
per-agent roster).

The bootstrap block instructs the main agent, at the start of **every** session, to:

1. Read all `.md` files in `.zcode/agents/`.
2. Register each agent under its filename (without `.md`) as an available subagent
   in its context (**prompt-level registration — there is no `define_subagent` API**).
3. Only then handle user requests (delegation to the orchestrator etc.).

**Open P6 real-repo test (V18):** whether workspace-level `.zcode/agents/`
auto-loads. If verified, the bootstrap block can be dropped config-only. The plugin
route (which distributes `agents/*.md` per workspace since 3.11.2) is verified as an
alternative distribution path.

## Project context (AGENTS.md)

- Loaded at **user-global and workspace level only** — no child-directory merging,
  no `@import` syntax (V2). Do not create subdirectory `AGENTS.md` files.
- `CLAUDE.md` is only read as a one-time migration by ZCode itself; agent-meta
  neither generates nor manages it.
- agent-meta writes the managed block (plus the ZCode bootstrap block) via the
  shared `templates/configs/AGENTS.project-template.md`.

## Workspace config (.zcode/config.json)

`.zcode/config.json` is the canonical, schema-documented workspace config (V6).

- **MCP** lives under the **nested key `mcp.servers`** (V2). agent-meta configures
  `mcp-config: {committed-file: .zcode/config.json, format: zcode-json}`. The
  `zcode-json` format writer **lands with the P3 commit**; until then sync warns
  and skips MCP generation. User-level config wins; **no merge** across levels.
- **Models are NOT written here** (V9): `model.main`/`model.lite` keys are not
  documented — model configuration is UI-managed in `~/.zcode/v2/config.json`.
  There is therefore no settings template for ZCode.
- `zcode.json` also exists as a project-override location, but no explicit
  precedence rule between it and `.zcode/config.json` is documented (V6 — open
  P6 nice-to-have).

## Models

Verified built-in IDs (V9): **`glm-5.3`** and **`glm-5.3-flash`** (Flash available
out of the box for subscriptions).

| Tier | Model ID |
|------|----------|
| `nano` | `glm-5.3-flash` |
| `fast` | `glm-5.3-flash` |
| `balanced` | `glm-5.3` |
| `powerful` | `glm-5.3` |
| `max` | `glm-5.3` |

Per-role models resolve **directly in the generated agent files**: subagent files
support a `model` frontmatter field (model ID or `inherit`; without override the
main model is inherited) — agent-meta injects `model` per role via the standard
resolution chain (`model: inject`, not skipped as the original plan sketched).
Unknown frontmatter keys are ignored by the harness (V2).

## Delegation

Native **`Agent`** tool (legacy alias **`Task`**, V17) with `subagent_type`,
`prompt` and `run_in_background` parameters.

- **Backgrounding:** `subagents.autoBackgroundMs` turns long calls into `/tasks`
  jobs; results are collected via `/tasks`.
- **`parallel_execution` is deliberately `false`:** backgrounding is not a verified
  parallel-subagent contract — fan-out in `delegation-syntax.yaml` issues multiple
  `Agent` calls in one response, but no native parallel guarantee is claimed.
- **Handoff:** conservative **YAML text block** (`handoff_format: yaml_text_block`,
  `handoff_envelope_support: false`) — no JSON envelope verified for ZCode.

Tool whitelist (`config/provider-tools.yaml`, `zcode`): `Bash`, `Read`, `Write`,
`Edit`, `Glob`, `Grep`, `WebFetch`, `WebSearch`, `TodoWrite`, `Agent`, `Task`,
`mcp__*`. `bash_tool_name: Bash` (`terminal_tool: Bash`) — all 1:1 names (V5).

## Hooks

ZCode supports 7 hook events (stdin = one JSON line, camelCase + snake_case,
Claude-compatible naming) — **BUT project-level hooks are completely ignored by
the harness** (`config_project_hooks_ignored`, V2). Hooks only take effect via a
plugin or at user level.

Consequence: `has_hooks: false` for project wiring — agent-meta generates no hook
files and no hook registration for ZCode.

## Verified surface (state 2026-09, ZCode 3.11.2)

| Surface | Fact |
|---|---|
| Subagents | User-level `~/.zcode/agents/<name>.md` auto-load; frontmatter `name`/`description` required, unknown keys ignored, `injectAgentsMd` default on |
| Skills | User + workspace scope (`.zcode/skills/<skill>/SKILL.md`) |
| Hooks | 7 events — project-level hooks ignored (see above) |
| MCP | User `~/.zcode/cli/config.json` + workspace `.zcode/config.json` (`mcp.servers`); user wins, no merge |
| Commands | User + workspace scope |
| Plugin | Bundles all five surfaces; per-workspace installable since 3.11.2 |

### What does agent-meta generate?

| Artifact | Behavior |
|----------|----------|
| `.zcode/agents/*.md` | Regenerated on every sync, stale files deleted (`model` injected per role; `tools` skipped; `memory`/`permissionMode`/`temperature`/... stripped) |
| `AGENTS.md` (managed block + bootstrap block) | Updated on every sync |
| `AGENTS.md` (rest) | Created once, then maintained manually |
| `.zcode/config.json` | Canonical workspace settings file; MCP (`mcp.servers`) writer lands with the P3 commit — until then sync warns + skips |
| Rules / Commands / Hooks | Not generated (`has_rules`/`has_commands`/`has_hooks` all `false`) |
| `.zcode/snippets/`, `.zcode/pending-tasks.md` (gitignored), `.zcode/3-project/` | Standard agent-meta artifacts |

## Deliberate limitations

1. **No parallel-execution flag** — backgrounding (`run_in_background` /
   `autoBackgroundMs`) is not a verified parallel contract.
2. **No JSON handoff envelope** — conservative YAML text block until verified.
3. **No project-level hooks** — the harness ignores them; no mirroring possible.
4. **No settings template / model keys** — models are UI-managed in
   `~/.zcode/v2/config.json`; per-role models ride in the agent files instead.
5. **No commands/skills sync adapters yet** — surfaces are verified, the
   capability list grows with P6.
