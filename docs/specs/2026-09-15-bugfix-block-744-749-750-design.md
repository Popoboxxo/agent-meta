## Problem

Three independent defects remain in the framework after the plugin-catalog
unification (`docs/superpowers/plans/2026-09-05-plugin-catalog-unification.md`).
They share a root cause pattern — a path or identifier that was renamed/deleted
but is still read, emitted, or documented under its old name.

**Bug A — #744, the artifact-freshness release gate reads its config from the
submodule path.** `hooks/1-generic/release-gates/artifact-freshness.sh` resolves
its opt-in config relative to the *consumer project root* as
`.agent-meta/generated-artifacts.yaml` (VERIFIED, `:48`; the header comment
`:5`, the config-convention comment `:36`, and the `[SKIP]` message `:50` all
name the same path). `.agent-meta/` is the agent-meta **submodule** mount point,
not project-owned configuration space. Every other project-level knob lives in
`.meta-config/` (for example the enabled-flag source
`.meta-config/project.yaml`, VERIFIED-RECON via
`scripts/lib/dod.py:380 resolve_release_gates`). Consequence: to activate the
gate a consumer must write configuration *into a submodule directory* — which is
either untracked, overwritten on submodule update, or plain impossible in
setups that keep the submodule read-only. The gate is opt-in and self-skips
when the file is missing (`:49-52`), so the defect is silent: the gate simply
never runs. `docs/RELEASE_GATES.md:191`, `:329`, `:368` and
`docs/CODEBASE_OVERVIEW.md:1166` teach the wrong path (VERIFIED).

**Bug B — #749, the `project-atlas` catalog entry advertises an invocation that
does not exist.** `config/plugin-catalog.yaml:370-387` (VERIFIED) declares key
`project-atlas`, `binary: project-atlas`, and
`connection: {type: stdio, command: project-atlas, args: [--mcp]}`. The upstream
binary is `projectatlas` (no hyphen) and the real host invocation carries
`--require-version <version> --db <repo>/.projectatlas/projectatlas.db --config
<repo>/.projectatlas/config.toml mcp` with `cwd: <repo>`; it is generated
per-repo by `projectatlas init` and cannot be expressed as a static catalog
pair. Moreover the loader cannot express the real form at all:
`availability-probe: command-v` prefers the `binary` string and runs
`shutil.which(binary)` / falls back to `connection.command` (VERIFIED,
`scripts/lib/plugins.py:83-85`), and the stdio builder reads only
`command` (string), `args` (list), `env` — `cwd` is not supported and is
silently ignored (VERIFIED, `scripts/lib/mcp_provider_config.py:134-147`).
`scripts/lib/plugin_test.py:166-176` probes `local-process` via
`shutil.which(conn.command)`. So today the entry is both misnamed and
mis-describing; probing it fails and the description still claims the values are
"verified at first real integration" (VERIFIED, `:377-378`).

**Bug C — #750, the generated MCP block points at a deleted file.** The MCP
renderer `_generate_rule_content()` (VERIFIED, `scripts/lib/mcp.py:55`) emits
`Details: `config/mcp-registry.yaml`` (`:93`) and the generator footer
`*Generiert von agent-meta aus `config/mcp-registry.yaml` — nicht manuell
bearbeiten.*` (`:110`). The same string is used as the stale-cleanup
`content_marker` (`:342`, consumed by
`scripts/lib/rule_index.py:45-107`). `config/mcp-registry.yaml` was deleted by
the plugin-catalog unification (VERIFIED — the file does not exist;
`tests/test_legacy_registries_removed.py:9` asserts its absence) and
`config/plugin-catalog.yaml` is the sole source (VERIFIED, `:13-14`). Twelve
generated provider artifacts therefore carry a reference to a non-existent
file, and live docstrings/comments plus two platform rule files repeat it
(VERIFIED: `scripts/lib/mcp.py:189`, `:377`; `scripts/lib/registry_query.py:121`;
`scripts/lib/skill_channel.py:157`; `rules/2-platform/agent-meta-mcp.yaml:4`;
`rules/2-platform/homeassistant-mcp.yaml:4`).

## Ziel (Goal)

1. **Bug A.** The artifact-freshness gate reads its opt-in config from
   **project-owned** configuration space: `.meta-config/generated-artifacts.yaml`
   relative to the consumer project root, with a documented fallback to
   `<project-root>/generated-artifacts.yaml` for projects that do not use
   `.meta-config/`. The submodule path `.agent-meta/generated-artifacts.yaml` is
   no longer read. Code, comments and documentation name the same path.
2. **Bug B.** The catalog entry no longer claims an invocation it does not own.
   The key and binary are corrected to `projectatlas` so the derived tool
   namespace is `mcp__projectatlas__*`, and the entry is explicitly marked as
   host-config generated by `projectatlas init` instead of implying a static,
   complete `command`/`args` pair. The entry stays `enabled-by-default: false`
   and binds no tools.
3. **Bug C.** Every live reference to `config/mcp-registry.yaml` in framework
   source, generated provider artifacts and current documentation is replaced by
   `config/plugin-catalog.yaml`, including the stale-cleanup marker, and a
   regression guard prevents the deleted path from reappearing in live sources.

### Bug A — config-path resolution in the gate

**IC-A1 — `hooks/1-generic/release-gates/artifact-freshness.sh` (shell entry point).**

The gate's only public interface is its config-path resolution plus its exit
code contract. Resolution happens after `cd "$PROJECT_ROOT"` (existing line
`:16-17`) and is project-root relative. Exit contract: `0` = pass **or**
self-skip (disabled, config missing, `python3` missing), non-zero = fail
(blocks the release) — unchanged from the header contract at `:8-12`.

Resolution order (first existing file wins):

| Order | Path (relative to project root) | Meaning |
|---|---|---|
| 1 | `.meta-config/generated-artifacts.yaml` | primary, project-owned, versionable |
| 2 | `generated-artifacts.yaml` | fallback for projects without a `.meta-config/` directory |
| 3 | — (none exists) | self-skip |

Concrete contract, replacing the assignment currently at `:48`:

```bash
CONFIG_FILE=""
for candidate in ".meta-config/generated-artifacts.yaml" "generated-artifacts.yaml"; do
  if [ -f "$candidate" ]; then
    CONFIG_FILE="$candidate"
    break
  fi
done
if [ -z "$CONFIG_FILE" ]; then
  echo "[SKIP] $GATE_NAME: no .meta-config/generated-artifacts.yaml or generated-artifacts.yaml found — opt-in check not configured"
  exit 0
fi
```

Edge/error paths:

- **Neither candidate exists** → print `[SKIP]` naming both candidates, `exit 0`.
  This preserves the opt-in semantics; the gate must never block a release
  merely because it is unconfigured.
- **Both candidates exist** → the `.meta-config/` path wins (order 1). This is
  deterministic and documented in the config-convention comment and in
  `docs/RELEASE_GATES.md`.
- **`PROJECT_ROOT` unset** → defaults to `$PWD` (unchanged, `:16`).
- **`cd "$PROJECT_ROOT"` fails** → `exit 1` (unchanged, `:17`). Not a config-path
  concern; do not change.
- **`.agent-meta/generated-artifacts.yaml` exists only** → the gate now
  self-skips. That is the intended breaking change for Bug A and must be called
  out in `docs/RELEASE_GATES.md` as a migration note.
- **No environment override for the path** is introduced. The path is resolved
  solely from the two candidates above; adding an override is out of scope
  (see Non-Goals).
- The parser, the freshness comparison (`resolve_mtime`, `:113-125`) and the
  `[FAIL]`/`[INFO]` output format are **not** part of this contract and must not
  change.

### Bug B — catalog entry

**IC-B1 — `config/plugin-catalog.yaml`, top-level key `projectatlas` (was
`project-atlas`, currently `:370`).**

New entry body (field order and comments are binding for reviewability; values
are binding):

```yaml
  projectatlas:
    kind: mcp-server
    origin-type: local-process
    availability-probe: command-v
    binary: projectatlas
    description: >-
      Project Atlas — local MCP-based repo knowledge-graph tool
      (https://github.com/styler-ai/ProjectAtlas). The upstream binary is
      `projectatlas` (no hyphen). The real host invocation is NOT a static
      catalog pair: it is generated per repository by `projectatlas init` and
      carries --require-version <version>, --db <repo>/.projectatlas/
      projectatlas.db, --config <repo>/.projectatlas/config.toml and cwd=<repo>.
      `projectatlas init` writes version-matched host configs (for example
      .projectatlas/projectatlas.opencode.json,
      .projectatlas/projectatlas.claude.mcp.json,
      .projectatlas/projectatlas.mcp.json). This catalog entry only records the
      binary and that host config generation is delegated to `projectatlas init`.
    config-generated-by: projectatlas init
    category: dev-tool
    enabled-by-default: false
    tools:
      allowed: []
    connection:
      type: stdio
      command: projectatlas
      args: []
    secrets: []
```

Contract details and edge paths:

- **Key rename.** `project-atlas` → `projectatlas`. The key is the MCP server id
  and feeds the generated tool namespace `mcp__{server}__{tool}`
  (`scripts/lib/agent_sync.py:107`, VERIFIED-RECON). After the rename the
  namespace is `mcp__projectatlas__*`.
- **`binary: projectatlas`.** Required so `command-v` probing
  (`scripts/lib/plugins.py:83-85`) and `local-process` probing
  (`scripts/lib/plugin_test.py:166-176`) look up the real executable name.
  With the old value `shutil.which("project-atlas")` returned `None` on a
  correctly installed host.
- **`connection.command: projectatlas`.** Must equal the real binary name; the
  loader's `command-v` fallback and the stdio builder
  (`scripts/lib/mcp_provider_config.py:134-147`) both read it.
- **`args: []`.** The catalog must not assert `--mcp` (the real invocation ends
  with the `mcp` subcommand and additionally requires `--require-version`,
  `--db` and `--config`), and it cannot assert the full argv because `--db` /
  `--config` / `cwd` are per-repo. An empty list is the honest representation:
  no false invocation is claimed. Populating the real argv is out of scope
  (Non-Goals) because `cwd` is not representable in the stdio builder.
- **`config-generated-by: projectatlas init`.** New explicit marker field. It is
  legal because `config/plugin-catalog.yaml` has no JSON schema — loading is
  `yaml.safe_load` plus a top-level mapping check
  (`scripts/lib/io.py:60-95`, VERIFIED-RECON), and the only catalog validation
  (`_validate_permitted_injections()`) applies exclusively to `kind: cli-tool`.
  Unknown fields are ignored by the loaders, so the marker is inert at runtime
  and purely documentary.
- **`enabled-by-default: false`, `tools.allowed: []`, `secrets: []`** unchanged.
  No permission, no agent frontmatter and no allowlist references
  `project-atlas` today (VERIFIED-RECON), so the rename touches no consumer
  wiring; `tools.allowed: []` binds no `mcp__*` tool before or after.
- **Error paths.** Loading the catalog with a missing/invalid entry yields the
  generic loader behaviour unchanged; this contract adds no new failure mode. The
  new `description` and `config-generated-by` are never parsed, so a malformed
  value cannot break sync.
- **Sync inertness — scoped, not unconditional (RVW-14).** The rename must not
  change any generated artifact **in this repository**, because the entry stays
  `enabled-by-default: false` and `.meta-config/project.yaml:84-92` activates
  only `honcho`, `playwright`, `reqogniloom` and `graphify` (VERIFIED-R2), so the
  entry never reaches the stdio builder here. The property is therefore only
  "no byte change **while the entry stays inactive**".
- **Documented behaviour once a project activates the entry.** If a consumer
  enables `projectatlas`, the stdio builder
  (`scripts/lib/mcp_provider_config.py:134-147`, VERIFIED-R2) emits provider
  config from `command`/`args` alone:
  - non-opencode branch (`:143-145`) sets `entry["command"] = cmd` and
    `entry["args"] = args` → `"command": "projectatlas"`, `"args": []`;
  - opencode branch (`:139-140`) sets `entry["command"] = [cmd] + args` →
    `["projectatlas"]`.

  Both forms are structurally valid but invocation-incomplete (`--require-version`,
  `--db`, `--config`, `cwd` are missing), because `cwd` is not representable
  (Non-Goals). `args: []` is therefore the **frozen, documented** representation:
  activating the entry before the stdio builder can express `cwd`/full argv yields
  a config that is honest about carrying no arguments rather than a false one.
  This consequence is a documented behaviour, not a defect of this bugfix.

This is the reviewable "no byte change while inactive" property of the fix.

**IC-C2 — `scripts/lib/mcp.py:342`, stale-cleanup marker.**

`content_marker` changes to
`"config/plugin-catalog.yaml\` — nicht manuell bearbeiten"`. The trailing
backtick and em-dash suffix are part of the marker and must be preserved
verbatim; the marker is passed to
`bootstrap_previously_managed()` (`scripts/lib/rule_index.py:45-107`) to decide
which previously generated files may be deleted.

**Actual resolution order (corrected, RVW-4).** The bootstrap is **index-first**,
not marker-first. `bootstrap_previously_managed(target_dir, index_path,
glob_pattern, content_marker=...)` (`rule_index.py:45-51`, VERIFIED-R2) returns
`read_managed_index(index_path)` immediately when the index exists and is
readable (`rule_index.py:78-84`, VERIFIED-R2). The caller passes
`target_dir / MCP_MANAGED_INDEX_FILENAME` (`scripts/lib/mcp.py:334`), where
`MCP_MANAGED_INDEX_FILENAME = ".agent-meta-managed-mcp"` (`mcp.py:48`,
VERIFIED-R2) — such an index exists in this repository (for example
`.gemini/rules/.agent-meta-managed-mcp`, VERIFIED-R2). The `content_marker`
comparison happens **only** in the glob fallback, i.e. when the index is absent
or unreadable (`rule_index.py:85-107`, marker check at `:105`, VERIFIED-R2).

Two consequences, and the second is a residual risk that must be documented
rather than mitigated by a claim:

1. **Marker ↔ footer round-trip.** The marker string must equal the footer
   substring emitted at `mcp.py:110`. Both strings change in the same
   commit/source edit; otherwise an index-less project cannot adopt
   *newly written* files in a later run. This is what stays binding.
2. **Residual orphan restfall in index-less projects (documented, not fixed).**
   In a project without a managed index, files previously written with the
   **old** marker are not recognized by the **new** marker and are therefore
   never swept — they survive as orphans. No ordering inside a single sync run
   can change that, because those files were produced by an earlier run with the
   old marker. The implementation must **not** claim "atomic ordering" as the
   mitigation; the correct statement is: the rename is safe for projects that
   have an index (the normal case — the index is written on every run at
   `mcp.py:382`), and for index-less legacy projects it leaves old-marker MCP
   rule files behind. These are documented as a known residual state, to be
   removed manually or by a later `sync.py` run after the index exists. Evidence
   for the index-less path: `tests/test_mcp_stale_cleanup.py:114-138`
   (VERIFIED-R2), which bootstraps an orphan without a prior index purely via the
   marker.

**Binding implementation order** (unchanged in effect, re-scoped):
(a) edit the source so marker and footer carry the new string in the same change,
(b) run `python scripts/sync.py` so every managed MCP artifact is rewritten with
the new marker and the index is refreshed, (c) rely on stale cleanup for
index-holding projects only.

```python
def test_no_live_source_references_deleted_registry():
    scan_roots = (
        # hand-authored framework sources
        "scripts", "hooks", "rules", "config", "agents",
        # generated provider artifacts (managed channel outputs)
        ".claude/skills", ".opencode/skills", ".gemini/rules",
    )
    suffixes = (".py", ".sh", ".yaml", ".yml", ".md")
    needle = "mcp-registry.yaml"
    allowlist = (
        "tests/fixtures/legacy-registries/",
        "docs/superpowers/plans/",

    offenders = []
    for root in scan_roots:
```

## Datenfluss (Data Flow)

**Bug A — gate invocation flow.**
`release-gates/pre-release-check.sh` dispatcher *or* a standalone
`bash release-gates/artifact-freshness.sh` →
`PROJECT_ROOT` resolution (`:= $PWD`) → `cd "$PROJECT_ROOT"` →
`source lib/hook_common.sh` → `hook_gate_check_enabled` reads the sync-baked
`PRE_RELEASE_GATE_ENABLED` → **config resolution (changed)**: probe
`.meta-config/generated-artifacts.yaml`, else `generated-artifacts.yaml`, else
self-skip `[SKIP]` + `exit 0` → `python3` inline parser reads `artifacts:`
pairs → per pair `resolve_mtime(source)` / `resolve_mtime(generated)` via
`git log` with filesystem-mtime fallback → `[FAIL]` lines + `exit 1` or
`[INFO]` + `exit 0`. Only the config-resolution node changes; inputs downstream
are unchanged.

**Bug B — catalog consumption flow.**
`config/plugin-catalog.yaml` → `scripts/lib/io.py` `yaml.safe_load` + top-level
mapping check → `load_mcp_registry()` slice of kind `mcp-server` →
`resolve_active_mcp_servers()` (entry is `enabled-by-default: false`, so it is
inactive unless a project opts in) → for active servers:
`_generate_rule_content()` (rule/skill channel) and
`generate_provider_configs()` (stdio builder reads `command`/`args`/`env`) →
sync log. Probing path: `probe_plugin_availability()` / `plugin_test.py` →
`shutil.which(binary)` → PASS/FAIL hint. Declared fields
`config-generated-by` and `description` are never consumed; `args: []` with an
inactive entry produces no artifact. Renaming the key changes the
`mcp__{server}__{tool}` namespace string, which is the observable identifier.

**Sync-time probe of the inactive entry (RVW-10).** The sync process *does*
evaluate `availability-probe` for inactive catalog entries: `_probe_inactive_plugins`
(`scripts/lib/plugins.py:101-114`, VERIFIED-R2) is invoked from
`scripts/lib/sync_pipeline.py:914-917` (VERIFIED-R2, only when `--check` is not
set) and calls `probe_plugin_availability` (`plugins.py:77-98`), which for
`command-v` resolves the `binary` field (`:84`, VERIFIED-R2). Consequence of the
`binary` correction: on a host where `projectatlas` is installed, sync output can
now contain the informational line
`[HINWEIS] Plugin 'projectatlas' lokal verfügbar, aber nicht aktiviert
(--test-plugin projectatlas zum Prüfen).` This is **stdout-only** and changes no
artifact — it is the intended effect of telling the truth about the binary name,
and it is explicitly acknowledged in the Non-Goals section instead of being denied.

**Bug C — MCP rule generation flow.**
`config/plugin-catalog.yaml` → `load_mcp_registry()` → per active server
`_generate_rule_content(server_name, server_def, compact=False)` →
(a) lazy channel: `write_skill_channel_rule()` into the provider rules/skills
dir, (b) embedded channel: `write_skill_channel_rule()` for non-native providers,
(c) `compact=True` embed into context files via
`scripts/lib/context.py:1677-1679`. The emitted Markdown now contains

agent sync, respectively; the platform YAML comment is inert.
