## 1. Root-Cause Bug Fix: Delegation-Syntax Laufzeit-Platzhalter

### Problem
LLM bei Runtime interpretierte `{{agent}}`, `{{task}}`, `{{calls}}`, `{{foreground}}`, `{{background}}` in der generierten Delegation-Syntax als **ungelöste sync.py-Platzhalter** und **weigerte sich zu delegieren**. 

Szenario:
```
Agent(subagent_type="{{agent}}", prompt="{{task}}")
```

LLM: "Das sieht aus wie ein Template-Fehler. Ich kann nicht delegieren wenn die Variablen nicht aufgelöst sind."

### Root-Cause
`config/delegation-syntax.yaml` verwendete doppelte geschweifte Klammern `{{}}` für Platzhalter, die der LLM zur Runtime füllen sollte. Syntax-Engine während Compile-Zeit interpretierte sie korrekt, aber LLM bei Runtime sah sie als ungelöste Template-Variablen.

### Fix
**Umgestellt auf `<angle-brackets>`** für alle Laufzeit-Platzhalter:
```yaml
delegate: "Agent(subagent_type=\"<ziel-agent>\", prompt=\"<vollständiger-task-text>\")"
fanout: "Agent(...)\nAgent(subagent_type=\"<agent_1>\", ...)\nAgent(subagent_type=\"<agent_2>\", ...)"
parallel_group: "Agent(...run_in_background=True)"
fallback: "Agent(..., prompt=\"<task>\")"
handoff: "JSON mit <quelle>, <ziel>, <schema-uri>, <parent-HOFF>"
```

LLM erkennt `<>` korrekt als Platzhalter die es konkret füllen soll.

**Dateien aktualisiert:**
- `config/delegation-syntax.yaml` (alle 5 Provider: Claude, Opencode, Gemini, Continue, Copilot)

**Impact:** Delegation war komplett broken, jetzt funktioniert alles wieder.

## 2. Issue #284: Orchestrator Pre-Delegation Self-Validation Gate

Neue Section `Pre-Delegation Gate (Pflicht vor jeder Delegation)` mit 3-Punkte-Checklist:

1. **Agent passt zum Intent?** (Intent-Routing-Tabelle konsultieren)
2. **Kein offener Dependency-Konflikt?** (Hängt dieser Task von noch laufenden parallelen Tasks ab?)
3. **Erwartetes Ergebnis konkret genug zu validieren?** (Vages "verbessere X" → erst präzisieren)

→ ALL drei "ja" → Delegation starten. ANY "nein" → erst lösen.

**Zweck:** Verhindert ungültige/mehrdeutige Delegationen die zu Rückfragen oder Fehlschlägen führen.

**Version:** `orchestrator.md` v3.22.0

## 3. Issue #283: Standardisiertes Context-Handoff-Format

Neue Section in Orchestrator `Envelope-Erstellung (vor jeder Delegation)` definiert Standardformat für `ctx` (Context):

```
TASK: <eine Zeile>
CONTEXT:
  - Branch: <name>
  - REQ-ID: <id oder n/a>
  - Vorherige Ergebnisse: <key findings in 1-2 Sätzen>
CONSTRAINTS:
  - Nicht anfassen: <Dateien/Bereiche falls zutreffend>
  - Muss verwenden: <Pattern/Standard falls vorgeschrieben>
EXPECTED_OUTPUT:
  - <konkret messbares Ergebnis>
```

Pflicht: `TASK` + `EXPECTED_OUTPUT`. Auch in Feature-Agent v1.8.0 integriert.

**Zweck:** Einheitliche Kommunikation zwischen Agenten, weniger Rückfragen, schnellere Eskalation.

## 4. Issue #282: In-Context Delegation Tracker

Orchestrator führt intern eine Tracker-Tabelle mit jeder Delegation:

| # | Agent | Task (Kurzform) | Status | Result-Key |
|---|-------|----------------|--------|------------|

**Regeln:**
- Nach jeder Delegation: Zeile hinzufügen / Status aktualisieren
- Vor neuer Delegation: **Duplikat-Check** — gleicher Agent + gleicher Task-Summary → nicht erneut dispatchen
- Nach jeder 3. Delegation: kompakte Status-Tabelle einmalig an User zeigen
- Context Guard (>5 Delegationen): Tracker auf 2-3 Zeilen komprimieren (nur offene/fehlgeschlagene behalten)

**Zweck:** Verhindert Duplikat-Delegationen, hilft User den Überblick zu behalten, Early-Warning für Komplexität.

## 5. Issue #281: BARRIER Protocol mit Widerspruchs-Handling

BARRIER() blockiert bis ALLE gestarteten parallelen Agenten geantwortet haben.

**Ablauf:**
1. Warten bis jeder Subagent ein Ergebnis liefert (kein Timeout-Skip)
2. Ergebnisse strukturiert wrappen:
   ```
   ||| agent=<name> result_key=<key> |||
   <Ergebnis-Text>
   |||
   ```
3. **Diff-Check** bei identischen Agenten-Typen (z.B. zwei `developer`-Instanzen):
   - Widersprechende Datei-Edits oder Entscheidungen? → User informieren, nicht auto-mergen
   - Konsistente Ergebnisse? → weiterfahren
4. Zusammenfassung an User: "[N] Agenten abgeschlossen. Weiter mit: [nächster Schritt]"

**Widerspruchs-Handling:**
```
[Agent-A] und [Agent-B] haben widersprechende Ergebnisse geliefert:
- Agent-A: [Kurzfassung]
- Agent-B: [Kurzfassung]
Bitte entscheide, welche Version weiterverwendet werden soll.
```

**Zweck:** Verhindert Merge von widersprüchlichen Änderungen, erhöht Reliability bei Parallel-Execution.

**Version:** `orchestrator.md` v3.22.0

## 6. Issue #286: Error-Recovery Matrix (erweitert)

Delegation-Fehlerbehandlung mit zwei neuen Szenarien:

| Fehler | Reaktion |
|--------|----------|
| Ambiguous result | Klärungsnachricht zurück zum Agent (1x Retry), dann User |
| Partial completion | Zeigen was fertig ist, User entscheiden lassen: weiter oder abbrechen |

Zusammen mit bestehenden:
- Permission/Unavailable → User informieren, Alternativen nennen
- Timeout → Max. 1 Retry mit anderem Tier, dann User
- Out-of-scope → Intent neu klassifizieren
- Multi-Failure → Sequentiell umschalten, User informieren

Nach 2 gescheiterten Delegationen für denselben Intent → User um Klärung bitten.

**Version:** `orchestrator.md` v3.22.0

## 7. Issue #285: Pipeline Execution-Mode Instructions

`scripts/lib/pipelines.py` erweitert um Execution-Mode-Headers pro Pipeline-Definition:

**Modi:**
- `sequential`: Schritte nacheinander, warten bis fertig
- `loop`: Generator → Critic → Feedback → Generator (max N Iterationen)
- `parallel_group`: Mehrere unabhängige Agenten parallel mit BARRIER

Jeder Schritt erhält Wait/Check-Cues (z.B. "warten auf Agent A", "Check auf Datei-Konflikte").

**Exportierte API:**
- `load_quality_pipelines()` — liest `config/role-defaults.yaml`
- `load_pipeline_overrides()` — liest `.meta-config/project.yaml`
- `apply_overrides()` — merged base+project-spezifisch, Stage-Level-Merging
- `validate_pipelines()` — prüft Agent-Existenz, Loop-Definitionen, Circular-Orchestration

**Zweck:** Macht Pipeline-Semantik explizit, ermöglicht automatische Orchestration, vereinfacht Konfiguration.

### `senior-developer.md` (v1.0.0, neu)
- **Tier:** `max`

4. Maximal 1 Eskalation pro Task — eskaliert auch Stufe 2, geht zum User

- Neue Zeilen in Intent-Tabelle mit {{#if DEVELOPER_TIERS_ENABLED}}-Blöcken
- Pre-Delegation Gate validiert Developer-Tier-Auswahl

**Zweck:** Cost-Optimierung (teuer Modelle sparen), bessere Task-Matching, klare Eskalationspfade.

## 9. PAL-Engine Bug: `{{#if PAL_*}}` Evaluation-Reihenfolge

### Problem
Inaktive `{{#if PAL_GEMINI}}`-Blöcke wurden fälschlicherweise durch `strip_inactive_conditional_blocks()` entfernt, **bevor** die PAL-Syntax-Engine sie substituieren konnte.

### Root-Cause
`_compose_agent()` in `scripts/lib/agents.py` rief `strip_inactive_conditional_blocks()` **vor** `DelegationSyntaxEngine.apply()` auf:

```python
content = strip_inactive_conditional_blocks(content, variables)  # FALSCH
content = pal_engine.apply(content, provider)  # Zu spät!
```

### Fix
**Reihenfolge umgestellt:** `{{#if PAL_*}}` Evaluation ZUERST:

```python
# 1. Evaluate {{#if PAL_*}} blocks for current provider
if provider in ["Gemini", "Claude", ...]:
    content = pal_engine.apply_conditional_blocks(content, provider)

# 2. DANN inactive blocks entfernen
content = strip_inactive_conditional_blocks(content, variables)

# 3. DANN finale PAL-Substitution
content = pal_engine.apply(content, provider)
```

**Dateien aktualisiert:**
- `scripts/lib/config.py` (Evaluation-Reihenfolge)
- `scripts/lib/agents.py` (Call-Reihenfolge in `_compose_agent()`)

**Impact:** Gemini, Continue, Copilot bekamen jetzt die richtigen Delegation-Instruktionen; vorher oft `None` oder falsche Provider-Syntax.

## Erkannte Probleme & Lösungsansätze

### Erkannt: Delegation-Syntax Verwirrung
- **Problem:** `{{}}` vs. `<>` bei Laufzeit-Platzhaltern unklar
- **Gelöst:** Neue Konvention: `{{}}` = Compile-Zeit (sync.py), `<>` = Runtime (LLM füllt)
- **Dokumentation:** `config/delegation-syntax.yaml` Kommentar-Header aktualisiert

### Erkannt: Scope-Creep bei Developer-Tier-Auswahl
- **Problem:** "Ist das ein junior oder developer-Task?" → User/Orchestrator oft unsicher
- **Gelöst:** Konkrete Signale in Developer-Tier-Tabelle (Typo, Off-by-one, etc.)
- **Eskalations-Protokoll:** Klar definiert, keine User-Bestätigung nötig

### Erkannt: Pipeline-Semantik zu implizit
- **Problem:** Ist eine Pipeline sequential oder parallel? User musste Konfiguration lesen
- **Gelöst:** Execution-Mode-Header + Wait/Check-Cues machen es explizit
- **Impact:** Orchestrator kann Pipelines automatisch orchestrieren (zukünftig)
